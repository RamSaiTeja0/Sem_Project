# TecSubstitution: Comprehensive Testing and Results Documentation

---

## 1. TESTING OBJECTIVES

Testing for the **TecSubstitution** platform was conducted systematically to validate the functional correctness, security, relational integrity, and operational robustness of the entire application. The primary objectives of the test suite were:

1. **Functional Correctness**: Verify that all core academic scheduling, catalog curation, daily attendance tracking, invigilation assignment, and peer substitution features behave strictly in accordance with institutional rules.
2. **Security & Authorization**: Validate that authentication guards, password complexity policies, session cookie signatures, and role-based permissions (`hos` vs `faculty`) strictly prevent unauthorized access or privilege escalation.
3. **Multi-Tenant Branch Isolation**: Guarantee that departmental boundaries are impregnable—ensuring that an HOS cannot view, alter, or delete another department's faculty, classes, timetables, or attendance records.
4. **Timetable Relational Integrity**: Ensure that timetable data models accommodate complex academic patterns (including multi-period laboratory blocks and non-teaching activity sessions) without data corruption or slot distortion.
5. **Availability Engine Correctness**: Ensure that the availability calculation engine reliably identifies genuinely free faculty for any specific period by cross-referencing master timetables, daily absence records, active exam invigilations, and accepted substitutions.
6. **Conflict & Double-Booking Prevention**: Verify that no teacher, classroom, or class section can ever be scheduled for two concurrent activities simultaneously, both at the application logic layer and at the database constraint level.
7. **Database Persistence & Survivability**: Ensure that all operational institutional data persists safely in a remote PostgreSQL database (Neon serverless) and fully survives server restarts without data loss.
8. **AI Extraction & Ingestion Reliability**: Validate that Google Gemini multimodal extraction output conforms strictly to the Phase B2.1 JSON schema, stages safely without mutating production tables, and enforces mandatory human HOS review.
9. **End-to-End Workflow Reliability**: Verify the real-world execution of end-to-end operational scenarios across multiple branches, accounts, and edge-case conflict conditions.

## 2. TESTING METHODOLOGY

The testing architecture of TecSubstitution employs a multi-tiered validation approach designed to test the system from atomic algorithms up to live HTTP server flows:

```
+-------------------------------------------------------------------------+
|                  TIER 5: LIVE REAL-WORLD E2E VERIFICATION               |
|      tests/live_verification.js (48/48 live browser/HTTP checks)        |
+-------------------------------------------------------------------------+
                                    │
+-------------------------------------------------------------------------+
|                  TIER 4: DATABASE & PERSISTENCE TESTS                   |
|      tests/database.test.js (30/30 checks)                              |
|      tests/neon_persistence_verification.test.js (10 Core Entities)     |
+-------------------------------------------------------------------------+
                                    │
+-------------------------------------------------------------------------+
|                  TIER 3: AI EXTRACTION & STAGING TESTS                  |
|      tests/gemini_n8n.test.js & tests/gemini_accuracy.test.js (8/8)     |
|      tests/staging_approval.test.js (17/17 checks)                      |
+-------------------------------------------------------------------------+
                                    │
+-------------------------------------------------------------------------+
|                  TIER 2: REST API & INTEGRATION SUITES                  |
|      Branch Isolation, Attendance, Invigilation, Substitution           |
+-------------------------------------------------------------------------+
                                    │
+-------------------------------------------------------------------------+
|                  TIER 1: CORE ENGINE & UNIT TESTS                       |
|      Availability Engine, Day/Period Normalizer, JSON Validator         |
+-------------------------------------------------------------------------+
```

1. **Unit Tests**: Directly target core domain logic in isolation, including day/period normalizers, contract schema validators, and availability scoring filters.
2. **Integration / API Tests**: Launch an in-process Express application to test HTTP routes, request validation, authentication middleware, error status codes, and JSON response formatting.
3. **Database Schema & Constraint Tests**: Run automated SQL migrations against a PostgreSQL target to confirm foreign keys, cascade rules, partial unique indexes, and idempotent re-runs.
4. **Neon Cloud Persistence Tests**: Connect to the remote Neon PostgreSQL database, create 10 distinct entity types, simulate a complete server teardown and restart, and confirm full state recovery.
5. **AI Pipeline & Staging Tests**: Feed real-world scanned timetable documents (`sample_timetable.jpeg`) through the Gemini extraction and validation pipeline, verifying schema adherence, entity mapping, and transactional live import.
6. **Live Real-World Verification**: An autonomous testing agent executes real HTTP requests over the network simulating full multi-department semester workflows from first-time HOS registration to peer substitution completion.

## 3. AUTHENTICATION AND AUTHORIZATION TESTING

Tested in `tests/auth.test.js`, `tests/accounts.test.js`, and `tests/branchisolation.test.js`.

### Verified Test Cases
- **Valid Credential Sign-In**: Confirmed that valid credentials issue a signed `tec_session` cookie containing user identity, role, and department.
- **Invalid Credential Rejection**: Confirmed that nonexistent usernames or incorrect passwords fail with HTTP 401 Unauthenticated.
- **Tampered Cookie Detection**: Modified signed session cookies were detected and rejected immediately via HMAC-SHA256 signature mismatch.
- **Strict Password Complexity Policy**: Enforced rejection of weak passwords failing the complexity regex (`min 6 chars, uppercase, lowercase, number, underscore`):
  - Rejected missing underscore (e.g., `abc123`).
  - Rejected missing number (e.g., `abcdef_`).
  - Rejected missing letter (e.g., `123456_`).
  - Rejected invalid symbols (e.g., `abc@123_`, `abc.123_`, `abc 123_`).
- **Role-Based Authorization Boundaries**:
  - Confirmed that Faculty users cannot access HOS administrative endpoints (HTTP 403 Forbidden).
  - Confirmed that HOS users cannot initiate or accept peer substitution requests (HTTP 403 Forbidden).
- **Multi-Tenant Branch Isolation**:
  - Confirmed that CME HOS cannot view, query, or mutate EEE faculty accounts or timetables (HTTP 403 Forbidden).
  - Confirmed that duplicate branch registration attempts return HTTP 403 (`"Branch code already exists"`).
- **Inactive Faculty Access Revocation**: Verified that deactivating a faculty account (`active = FALSE`) immediately blocks subsequent sign-in attempts while preserving historical timetable records.

- **Multi-Period Lab Blocks**: Confirmed that laboratory sessions spanning multiple periods (e.g., Periods 1 to 3) expand into atomic period slots during live storage while maintaining visual continuity in the grid.
- **Non-Teaching Activity Slots**: Confirmed that non-faculty periods (TPC, Library, Sports, Counselling) occupy class time without requiring an assigned instructor.

## 5. ATTENDANCE TESTING

Tested in `tests/faculty_attendance.test.js`.

### Verified Test Cases
- **Default Present State**: Verified that all active faculty members are treated as `PRESENT` when no absence record exists for a date.
- **HOS Absence Marking**: Verified that the HOS can mark a faculty member `ABSENT` on a specific calendar date (`YYYY-MM-DD`) with optional remarks via `POST /api/attendance`.
- **Date-Specific Granularity**: Confirmed that marking an instructor absent on Monday does not affect their availability on Tuesday or subsequent weeks.
- **Automatic Availability Filtering**: Verified that when availability is queried for a calendar date, faculty marked `ABSENT` on that date are excluded from the pool of free substitute candidates.
- **Restoration to Present**: Confirmed that deleting an absence record (`DELETE /api/attendance/:id`) restores the instructor's default present status.
- **Faculty Read-Only View**: Verified that instructors can inspect their personal attendance records (`GET /api/attendance/my`) but are blocked from creating or modifying attendance records (HTTP 403 Forbidden).

## 6. AVAILABILITY TESTING

Tested in `tests/availability.test.js`, `tests/cross_branch_availability.test.js`, and `tests/b7_4_availability_candidates.test.js`.

### Verified Test Cases
- **Free Faculty Identification**: Verified that instructors with no scheduled classes, absences, exam duties, or accepted substitutions are correctly classified as `FREE`.
- **Teaching Conflict Detection**: Instructors scheduled to teach a class in the master timetable are classified as `BUSY`.
- **Absence Conflict Detection**: Instructors marked absent on the target date are classified as `BUSY`.
- **Exam Invigilation Conflict Detection**: Instructors on active exam invigilation duty during the queried period are classified as `BUSY`.
- **Accepted Substitution Conflict Detection**: Instructors committed to covering another class during the slot are classified as `BUSY`.
- **Inactive Faculty Exclusion**: Instructors marked `inactive` or `on_leave` are excluded from candidate results.
- **Same-Branch-First Prioritization**: Confirmed that candidate results are partitioned into:
  1. `Priority Branch`: Free colleagues from the same academic branch as the absent instructor.
  2. `Other Branches`: Free colleagues from allied campus departments, providing fallback coverage when local staff are fully occupied.

## 8. FACULTY SUBSTITUTION TESTING

Tested in `tests/b7_5_substitution.test.js`.

### Verified Test Cases
- **Peer Request Creation**: Verified that an absent instructor (Faculty A) can dispatch a substitution request to an eligible free colleague (Faculty B) via `POST /api/substitutions/requests`.
- **Pending Record Ingestion**: Confirmed that the request is stored in `faculty_substitutions` with status `PENDING`.
- **Colleague Acceptance**: Confirmed that Faculty B can accept the request (`POST /api/substitutions/:id/accept`), transitioning the status to `ACCEPTED`.
- **Colleague Rejection**: Confirmed that Faculty B can decline the request with a rejection reason, updating the status to `REJECTED` and allowing Faculty A to choose another candidate.
- **Real-Time Revalidation Guard**: Verified that when Faculty B clicks Accept, the server performs an atomic check. If Faculty B was booked for another duty in the interim, the acceptance is aborted with HTTP 409 Conflict (`"Substitute is no longer free"`).
- **Master Timetable Immutability**: Confirmed that throughout the substitution lifecycle, the live `timetable` table is completely untouched.
- **HOS Read-Only Audit**: Verified that the HOS can view branch substitution history (`GET /api/substitutions`) but is blocked from approving or creating substitutions.

In an educational institution, timetable configurations, attendance records, and substitutions represent legal academic records. Persistence testing verifies that data is not merely cached in server RAM, but is durably stored in PostgreSQL with ACID guarantees, ensuring full survivability across server restarts or cloud redeployments.
