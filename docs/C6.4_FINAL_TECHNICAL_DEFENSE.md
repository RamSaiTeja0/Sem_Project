## SECTION 1 — BACKEND ARCHITECTURE

### Q1.1: How is the backend structured?
> **Answer**: The backend is structured using a modular layered architecture in Node.js and Express.js:
> - **Entrypoint (`server.js`)**: Configures Express, mounts middleware, defines static asset routing, and bootstraps the PostgreSQL database connection.
> - **Routing Layer (`src/routes/`)**: Contains distinct route modules (`auth.js`, `entries.js`, `timetable.js`, `availability.js`, `attendance.js`, `invigilation.js`, `substitutions.js`, `staging.js`, `uploads.js`).
> - **Domain & Logic Core (`src/core/`)**: Houses core algorithmic engines (`availabilityEngine.js`, `session.js`, `validator.js`, `normalizer.js`, `contractValidator.js`, `entityResolver.js`).
> - **Data & Cache Layer (`src/data/`)**: Coordinates in-memory caching and business entities (`store.js`, `departments.js`, `users.js`, `attendance.js`, `invigilation.js`, `substitutions.js`, `uploads.js`).
> - **Database Layer (`src/db/`)**: Manages the PostgreSQL connection pool (`pool.js`), SQL DDL schema migrations (`schema.sql`), and relational CRUD repositories (`repository.js`).

### Q1.2: Why Node.js?
> **Answer**: Node.js operates on an event-driven, non-blocking asynchronous I/O model. In an academic institution where multiple teachers query schedules and submit substitution requests concurrently, Node.js handles concurrent I/O operations with low memory overhead without thread-locking.

### Q1.3: Why Express.js?
> **Answer**: Express is a minimalist, flexible web framework. It provides robust HTTP routing, middleware pipelining, request payload parsing, and standard error handling without the rigid conventions or overhead of heavy enterprise frameworks.

### Q1.4: What are routes?
> **Answer**: Routes are endpoint definitions that bind specific HTTP methods and URL paths (e.g., `POST /api/timetable/entries`, `GET /api/availability`) to controller functions that process requests and deliver responses.

### Q1.5: What are middleware functions?
> **Answer**: Middleware functions execute during the HTTP request-response cycle before reaching the route controller. They inspect, transform, or reject requests. In our system, middleware handles JSON parsing, signed cookie decoding (`session.middleware`), role authorization (`requireHOS`, `requireFaculty`), and departmental branch scoping.

### Q1.6: Where is business logic implemented?
> **Answer**: Business logic is separated between `src/core/` (pure algorithmic logic such as availability calculations, contract validation, and entity resolution) and `src/data/` / `src/db/repository.js` (persistence, slot conflict verification, and state transition handling).

### Q1.7: How does the backend communicate with PostgreSQL?
> **Answer**: Through the native `pg` client library using a connection pool (`src/db/pool.js`). All SQL interactions use parameterized queries (`$1, $2`) to guarantee performance and security.

### Q1.8: How does the frontend communicate with the backend?
> **Answer**: The frontend uses standard asynchronous `fetch()` HTTP requests exchanging JSON payloads over RESTful routes, sending and receiving signed HTTP cookies automatically.

### Q1.9: What is a REST API?
> **Answer**: Representational State Transfer (REST) is a software architectural style that uses stateless communication and standard HTTP methods to perform operations on URI-identified resources.

### Q1.10: What HTTP methods are used in this project?
> **Answer**:
> - `GET`: Read resources (timetables, availability, attendance, staging preview).
> - `POST`: Create resources (add timetable entry, mark absence, request substitution, accept substitution).
> - `PUT`: Update existing resources (edit timetable entry, modify attendance remark).
> - `DELETE`: Remove resources (delete timetable entry, cancel substitution, clear absence).

### Q1.11: How are HTTP status codes used?
> **Answer**:
> - `200 OK`: Successful read or update.
> - `201 Created`: Successful creation of an entry, user, or substitution.
> - `400 Bad Request`: Malformed payload or validation failure.
> - `401 Unauthorized`: Unauthenticated request (missing or invalid session).
> - `403 Forbidden`: Authenticated user lacks required role or branch authority.
> - `404 Not Found`: Target entity or route does not exist.
> - `409 Conflict`: Business clash (double-booking, class slot occupied, race condition).
> - `422 Unprocessable Entity`: AI contract syntax error or unresolved catalog entity.
> - `500 Internal Server Error`: Unexpected server or database exception.

### Q1.12: How are errors handled?
> **Answer**: Synchronous and asynchronous errors are caught in route handlers and forwarded to Express error-handling middleware (`server.js`), which serializes clean, standardized JSON responses (`{ error, code }`) and logs server traces without exposing raw SQL stack traces to clients.

## SECTION 2 — AUTHENTICATION

### Q2.1: Explain the login flow.
> **Answer**: The client sends `{ username, password }` via `POST /api/auth/login`. The server queries `src/data/users.js`, retrieves the account, validates that `active === true`, verifies the password hash, generates a signed cookie (`tec_session`), and returns the user profile.

### Q2.2: How is the session created and stored?
> **Answer**: We use **stateless cryptographically signed cookies** implemented in `src/core/session.js`. The server packages `{ id, username, name, role, department, exp }` into a JSON string, Base64URL-encodes it, and signs it using an HMAC. The combined string is set as the `tec_session` cookie. **Zero session data is stored in server memory or database.**

### Q2.3: How does HMAC-SHA256 signing work?
> **Answer**: The server creates a cryptographic hash of the Base64URL payload using its private `SESSION_SECRET`:
> $$\text{Signature} = \text{Base64URL}(\text{HMAC-SHA256}(\text{Payload}, \text{Secret}))$$
> The cookie format is `Payload.Signature`. If any character in the payload is altered by a client, the server's recomputed signature will not match.

### Q2.4: How is timing attack prevention implemented?
> **Answer**: When verifying signatures in `src/core/session.js`, the server uses `crypto.timingSafeEqual(bufA, bufB)`. This ensures that comparing two tokens takes constant execution time regardless of how many bytes match, preventing timing analysis attacks.

### Q2.5: How are passwords hashed and validated?
> **Answer**: Passwords are encrypted using cryptographic hashing before database storage. During authentication, the submitted password is treated with the same hashing function and verified against the stored hash.

### Q2.6: What is the password complexity validation policy?
> **Answer**: Account creation enforces a strict complexity regex: minimum 6 characters containing at least one uppercase letter (`A-Z`), one lowercase letter (`a-z`), one digit (`0-9`), and an underscore (`_`). Passwords lacking any of these or containing unauthorized symbols are rejected with HTTP 400.

### Q2.7: What authentication middleware exists?
> **Answer**:
> - `session.middleware`: Runs on every request, parses `tec_session`, verifies HMAC signature and expiry, and attaches `req.session`.
> - `requireAuth`: Enforces that `req.session` exists; redirects page requests to `/login` or returns HTTP 401 for API calls.

### Q2.8: How is an inactive account handled?
> **Answer**: In `users.js`, the query checks `active === true`. If an administrator deactivates an account, login fails immediately, and active sessions are rejected upon token re-check.

> [!IMPORTANT]
> **Authentication Claim Boundary**: TecSubstitution does **not** use JSON Web Tokens (JWT), OAuth 2.0, or external Single Sign-On (SSO). It uses lightweight, stateless HMAC-SHA256 signed HTTP cookies.

## SECTION 3 — ROLE-BASED ACCESS CONTROL (RBAC)

### Q3.1: What are the distinct permissions of the Head of Section (HOS)?
> **Answer**:
> - Manage department branch configuration.
> - Provision and update faculty accounts.
> - Manage classes, classrooms, and subject catalogs.
> - Add, update, and vacate master class timetable entries.
> - Log and update daily faculty attendance (Present/Absent).
> - Assign exam invigilation duties directly and review faculty requests.
> - Upload timetable files, inspect AI staging, map entities, and execute live import.
> - Access read-only historical substitution audit ledgers.

### Q3.2: What are the distinct permissions of a Faculty Member?
> **Answer**:
> - View personal weekly teaching schedule.
> - Inspect vacant teaching periods.
> - Query available substitute colleagues across departments.
> - Initiate peer substitution requests to free colleagues.
> - Accept or reject incoming substitution requests from peers.
> - Cancel unaccepted pending substitution requests.
> - View personal attendance ledger in read-only mode.
> - Submit requests for exam invigilation duties.

### Q3.3: How are unauthorized routes blocked?
> **Answer**: Through dedicated route guard middleware:
> - `requireHOS` in `src/routes/entries.js`, `src/routes/attendance.js`, and `src/routes/staging.js` blocks requests where `req.session.role !== 'hos'` with HTTP 403 Forbidden.
> - `requireFaculty` in `src/routes/substitutions.js` blocks requests where `req.session.role !== 'faculty'` with HTTP 403 Forbidden.

## SECTION 4 — BRANCH ISOLATION

### Q4.1: How is a branch represented in the database?
> **Answer**: In the `departments` table via `code` (e.g., `CME`, `EEE`, `CSE`), `name`, `academic_year`, `semester`, and `active`. Related tables reference `department_id` or store `department_code`.

### Q4.2: How do users inherit branch ownership?
> **Answer**: When an HOS registers a faculty account, the backend automatically assigns `req.session.department` to the new record. Faculty accounts cannot edit or reassign their department code.

### Q4.3: How are HOS queries scoped?
> **Answer**: In `src/routes/entries.js`, `src/routes/faculty.js`, and `src/routes/attendance.js`, every query filters explicitly by `department_code = req.session.department`.

### Q4.4: Why is hardcoded department logic avoided?
> **Answer**: Department codes are completely dynamic. The system queries the `departments` table dynamically, allowing institutions to register new branches (e.g., `AI_DS`, `MECH`) without altering backend source code.

### Q4.5: Why is cross-branch availability permitted while management is isolated?
> **Answer**: Management requires administrative authority (only CME HOS manages CME classes). However, when checking substitution availability, discovering free teachers in allied departments enables coverage when local staff are fully engaged, maximizing institutional teacher utilization.

### Q4.6: Scenario: What happens if HOS A requests Faculty from Branch B?
> **Answer**: The endpoint intercepts the request in `src/routes/faculty.js`, detects that `req.session.department !== targetDepartment`, and responds with `HTTP 403 FORBIDDEN: Cross-branch access forbidden`.

### Q4.7: Scenario: What happens if Faculty A tries to modify Faculty B's timetable?
> **Answer**: Timetable modifications require `POST /api/timetable/entries`, which is guarded by `requireHOS`. The request is rejected with `HTTP 403 FORBIDDEN`.

### Q4.8: Scenario: What happens if a malicious user alters a branch parameter in the URL?
> **Answer**: The server ignores client-supplied department parameters for write actions and strictly extracts the verified department from the cryptographically signed `req.session.department`.

## SECTION 5 — DATABASE DESIGN

### Q5.1: Why PostgreSQL?
> **Answer**: Academic scheduling requires strong relational consistency. PostgreSQL provides robust ACID transactions, foreign keys, cascade rules, and partial unique indexes to guarantee zero scheduling collisions.

### Q5.2: What are the primary keys and foreign keys in your schema?
> **Answer**:
> - `departments`: Primary Key `id`.
> - `rooms`: Primary Key `id`.
> - `faculty`: Primary Key `id`, Foreign Key `department_id REFERENCES departments(id)`.
> - `subjects`: Primary Key `id`, Foreign Key `department_id REFERENCES departments(id)`.
> - `classes`: Primary Key `id`, Foreign Key `department_id REFERENCES departments(id)`.
> - `timetable`: Primary Key `id`, Foreign Keys to `classes(id)`, `subjects(id)`, `faculty(id)`, `rooms(id)`.
> - `faculty_attendance`: Primary Key `id`, Foreign Key `faculty_id REFERENCES faculty(id)`.
> - `exam_invigilation`: Primary Key `id`, Foreign Key `faculty_id REFERENCES faculty(id)`.
> - `faculty_substitutions`: Primary Key `id` (Text UUID), Foreign Keys to `faculty(id)`.

### Q5.3: What unique constraints and indexes exist?
> **Answer**:
> - `timetable_class_slot_unique`: `UNIQUE(class_id, day_of_week, period)`
> - `timetable_faculty_slot_unique`: Partial unique index on `(faculty_id, day_of_week, period) WHERE faculty_id IS NOT NULL`
> - `timetable_room_slot_unique`: Partial unique index on `(room_id, day_of_week, period) WHERE room_id IS NOT NULL`
> - `faculty_attendance_unique`: `UNIQUE(faculty_id, attendance_date)`
> - `exam_invigilation_unique`: `UNIQUE(faculty_id, exam_date, period)`

### Q5.4: How are transactions used?
> **Answer**: In `src/db/repository.js`, staged timetable imports execute inside a single transaction (`BEGIN` ... `COMMIT` / `ROLLBACK`). If any cross-class conflict occurs during span expansion, the entire import rolls back cleanly.

### Q5.5: How is Neon PostgreSQL configured?
> **Answer**: Configured via `DATABASE_URL` in `.env`. The connection pool (`src/db/pool.js`) enforces SSL mode (`sslmode=require`) and connection limits for serverless compatibility.

## SECTION 6 — TIMETABLE ENGINE

### Q6.1: How are class and faculty timetables represented?
> **Answer**: Both are derived from the single `timetable` table. A class timetable queries `WHERE class_id = $1`. A faculty timetable queries `WHERE faculty_id = $1`.

### Q6.2: How are temporal days and periods represented?
> **Answer**: Days are stored as strings (`Monday` through `Saturday`) validated against `src/core/normalizer.js`. Periods are stored as integers (1 to 7).

### Q6.3: What session types exist?
> **Answer**: Enforced by a check constraint:
> - `theory`: Standard 1-period instructional lecture.
> - `lab`: Practical laboratory session spanning multiple periods.
> - `activity`: Non-instructional session (Library, TPC, Sports) occupying class time with `faculty_id IS NULL`.

### Q6.4: Explain the three conflict dimensions enforced by the engine.
> **Answer**:
> 1. **Class Conflict**: The class section is already occupied in that day/period.
> 2. **Faculty Double-Booking**: The instructor is already teaching another class in that day/period.
> 3. **Room Conflict**: The physical room is already occupied by another class in that day/period.

## SECTION 7 — ATTENDANCE ENGINE

### Q7.1: What is the structure of `faculty_attendance`?
> **Answer**: Contains `id`, `faculty_id`, `attendance_date` (DATE), `status` (`PRESENT` or `ABSENT`), `marked_by`, and timestamps. A unique constraint `(faculty_id, attendance_date)` prevents duplicate records.

### Q7.2: What is the exact difference between PRESENT and ABSENT?
> **Answer**:
> - **PRESENT**: The faculty member is on campus and available to be considered for teaching or substitution based on their hourly period schedule.
> - **ABSENT**: The faculty member is unavailable for the **entire calendar date**. The availability engine completely excludes them from all candidate lists on that date.

### Q7.3: Does absence modify the recurring master timetable?
> **Answer**: No. Absence is date-specific. The weekly master timetable remains untouched, preserving regular schedules for subsequent weeks.

## SECTION 8 — AVAILABILITY ENGINE

### Q8.1: Explain the exact evaluation sequence of the Availability Engine.
> **Answer**: In `src/core/availabilityEngine.js`, for a given date, day, and period, the engine evaluates each instructor in this exact order:
> 1. **Active Check**: If `status !== 'active'`, mark **BUSY (INACTIVE)**.
> 2. **Attendance Check**: If marked `ABSENT` on that date in `faculty_attendance`, mark **BUSY (ABSENT)**.
> 3. **Master Timetable Check**: If assigned to a class in `timetable` for that day/period, mark **BUSY (TEACHING)**.
> 4. **Exam Invigilation Check**: If assigned to an active exam in `exam_invigilation` for that date/period, mark **BUSY (INVIGILATION)**.
> 5. **Accepted Substitution Check**: If committed to an accepted substitution in `faculty_substitutions` for that date/period, mark **BUSY (SUBSTITUTION)**.
> 6. **Free**: If none of the above match, the instructor is classified as **FREE**.

### Q8.2: How are candidate results ordered?
> **Answer**: FREE candidates are partitioned into two priority tiers:
> 1. **Priority Branch**: Free instructors belonging to the same department as the absent teacher.
> 2. **Other Branches**: Free instructors belonging to allied campus departments.

### Q8.3: Why is availability strictly read-only?
> **Answer**: To prevent side effects. Checking who is free must never mutate database records or auto-assign substitutes.

## SECTION 9 — EXAM INVIGILATION

### Q9.1: How are examination duties scheduled?
> **Answer**: Either directly by the HOS (`POST /api/invigilation`) or via faculty requests (`POST /api/invigilation/requests`) approved by the HOS.

### Q9.2: How does invigilation affect availability without marking a teacher absent?
> **Answer**: An active invigilation row creates a period-specific conflict. The teacher is marked **BUSY (INVIGILATION)** during those specific exam periods, but remains present on campus and eligible during their unassigned periods.

### Q9.3: What prevents duplicate invigilation assignments?
> **Answer**: The database constraint `CONSTRAINT exam_invigilation_unique UNIQUE (faculty_id, exam_date, period)`.

## SECTION 10 — SUBSTITUTION ENGINE

### Q10.1: Explain the exact implementation of the Option A workflow.
> **Answer**:
> 1. Absent Faculty A identifies a vacant teaching slot.
> 2. Faculty A queries the Availability Engine; the system verifies Faculty B is active, present, and free.
> 3. Faculty A submits a request via `POST /api/substitutions/requests`.
> 4. The request is stored in `faculty_substitutions` with status `PENDING`.
> 5. Faculty B logs in, reviews the request, and clicks Accept (`POST /api/substitutions/:id/accept`).
> 6. **Atomic Revalidation**: The server re-evaluates Faculty B's real-time availability.
> 7. If still free, status transitions to `ACCEPTED`; if no longer free, the acceptance is aborted with HTTP 409 Conflict.

### Q10.2: What are the lifecycle states of a substitution?
> **Answer**: `PENDING`, `ACCEPTED`, `REJECTED`, and `CANCELLED`.

### Q10.3: Why does the HOS have only read-only visibility into peer substitutions?
> **Answer**: In technical colleges, morning absences require rapid coverage before the first bell. Mandating HOS approval creates an administrative bottleneck. Peer-to-peer delegation empowers teachers to arrange coverage in minutes, while the HOS maintains full audit oversight via `GET /api/substitutions`.

## SECTION 11 — CONCURRENCY AND RACE CONDITIONS

### Q11.1: What if Faculty B is free when requested, but becomes busy before clicking Accept?
> **Answer**: Handled by **real-time atomic revalidation** at acceptance time. The server runs a live availability query inside the acceptance handler. If Faculty B was booked in the interim, the request is aborted with `HTTP 409 CONFLICT: Substitute is no longer free`.

### Q11.2: What if two absent teachers send substitution requests to the same Faculty B?
> **Answer**: Both requests exist as `PENDING`. Whichever request Faculty B accepts first will commit. If Faculty B subsequently attempts to accept the second request, the revalidation guard detects the conflict and rejects it.

### Q11.3: What prevents simultaneous double-booking during database writes?
> **Answer**: PostgreSQL's transaction isolation combined with partial unique constraints (`timetable_faculty_slot_unique`, `exam_invigilation_unique`) guarantees that two concurrent transactions attempting to insert colliding records will result in one committing and the other throwing a unique violation error.

## SECTION 12 — AI + N8N EXTRACTION PIPELINE

### Q12.1: Explain the complete AI extraction pipeline.
> **Answer**:
> 1. HOS uploads an image/PDF via `POST /api/uploads`; stored on disk; recorded in `timetable_uploads`.
> 2. Webhook triggers n8n workflow.
> 3. n8n fetches file binary via `GET /api/internal/uploads/:id/file` authenticated by `X-Internal-Secret`.
> 4. n8n forwards binary + Phase B2.1 prompt to Google Gemini 2.5 Flash.
> 5. Gemini extracts days, periods, classes, and lab spans, returning structured JSON.
> 6. n8n delivers JSON to `POST /api/internal/uploads/:id/processed`.
> 7. Backend validator evaluates contract rules; stores payload in `timetable_staging` (status: `VALID` or `INVALID`).
> 8. HOS reviews preview grid, resolves uncatalogued entity names via `map-entity`, and clicks Approve.
> 9. Live importer executes transactional commit to `timetable`.

### Q12.2: Why can't Gemini write directly to PostgreSQL?
> **Answer**: LLMs are non-deterministic and can hallucinate or misread abbreviated teacher names. Direct database writes could silently overwrite existing timetables or inject corrupt data. Staging enforces a mandatory human-in-the-loop safety boundary.

### Q12.3: What happens if an extracted teacher name cannot be matched to the catalog?
> **Answer**: The entity resolver (`src/core/entityResolver.js`) flags the reference as `UNRESOLVED`. The approval endpoint (`POST /api/staging/:id/approve`) returns HTTP 422 Unprocessable Entity, blocking live import until the HOS maps the name.

## SECTION 16 — DESIGN DECISION JUSTIFICATIONS

- **Why PostgreSQL instead of MongoDB?** Timetables are inherently relational; PostgreSQL enforces unique constraints at the database level to prevent double-booking.
- **Why Express over NestJS/Django?** Lightweight, zero boilerplate, transparent middleware execution, and low memory consumption.
- **Why signed cookies over JWT?** Stateless, zero database lookups, instant revocation capability, and immune to JWT header confusion attacks.
- **Why peer-to-peer substitution over HOS approval?** Eliminates early morning administrative bottlenecks; classes get covered in minutes while HOS retains full audit oversight.
- **Why keep master timetable unchanged?** Substitutions are temporary daily arrangements; modifying the master schedule would destroy the recurring weekly curriculum.
- **Why isolated AI staging?** Guarantees that AI hallucinations or OCR misreads can never silently corrupt production academic schedules.

## SECTION 17 — IMPLEMENTATION-BASED TRICK QUESTIONS

### Q17.1: If AI extracts incorrect data, what prevents bad data entering the database?
> **Answer**: Two barriers: first, the Phase B2.3 contract validator blocks syntax errors (`INVALID`); second, the entity resolution gate blocks approval if any extracted teacher/subject name does not match the active branch catalog.

### Q17.2: If a substitute becomes busy after the request is sent, what happens?
> **Answer**: At the moment the colleague clicks Accept, the server re-evaluates their live availability. If a conflict occurred, acceptance is aborted with HTTP 409 Conflict.

### Q17.3: Can the HOS approve a faculty substitution?
> **Answer**: **No.** HOS accounts are restricted from approving peer substitutions; the workflow is strictly faculty-to-faculty.

### Q17.4: Does an exam invigilation duty make a faculty member absent?
> **Answer**: **No.** Invigilation is an active duty. The teacher is present on campus and only marked BUSY during the exam periods.

### Q17.5: Can AI directly write to PostgreSQL?
> **Answer**: **No.** Gemini and n8n hold zero database credentials and can only deliver data to internal staging endpoints.

## SECTION 20 — TOP 15 TECHNICAL QUESTIONS TO MEMORIZE

1. **How is double-booking prevented?**  
   *Pre-validated by in-memory availability algorithms and physically enforced by PostgreSQL partial unique indexes (`timetable_faculty_slot_unique`, `timetable_room_slot_unique`).*  
   *Terms: In-Memory Validation, Partial Unique Indexes.*

2. **Explain the peer substitution workflow.**  
   *Absent Faculty A selects free Faculty B $\to$ sends request $\to$ Faculty B reviews and accepts $\to$ server executes atomic availability revalidation $\to$ commits to `faculty_substitutions` overlay.*  
   *Terms: Option A, Atomic Revalidation, Overlay.*

3. **Why doesn't the HOS approve peer substitutions?**  
   *To avoid morning administrative bottlenecks. Classes can be covered in minutes while the HOS retains read-only audit visibility.*  
   *Terms: Peer Delegation, Administrative Bottleneck, Audit Log.*

4. **Is the master timetable changed during a substitution?**  
   *No. Accepted substitutions are stored in a separate overlay table, keeping regular weekly schedules pristine.*  
   *Terms: Overlay Record, Master Timetable Immutability.*

5. **What is the difference between ABSENT, BUSY, and FREE?**  
   *ABSENT: on leave for entire day. BUSY: on campus but occupied by class, exam, or substitution. FREE: on campus and unoccupied.*  
   *Terms: Date-Specific Absence, Period-Specific Busy, Candidate Free.*

6. **How does exam invigilation affect availability?**  
   *Marks the teacher BUSY during exam periods without marking them absent from campus.*  
   *Terms: Period-Specific Conflict, Active On-Campus Duty.*

7. **Why use PostgreSQL on Neon instead of MongoDB?**  
   *Academic schedules are relational; PostgreSQL guarantees referential integrity, ACID transactions, and unique constraint enforcement.*  
   *Terms: Relational Integrity, ACID, Unique Constraints.*

8. **How does the AI timetable extraction work?**  
   *Image/PDF $\to$ n8n $\to$ Gemini 2.5 Flash $\to$ Phase B2.1 JSON $\to$ Validation Gate $\to$ Staging Table $\to$ HOS Approval $\to$ Live Import.*  
   *Terms: Gemini Multimodal, n8n Bridge, B2.1 Contract, Staging Table.*

9. **Why can't Gemini directly write to PostgreSQL?**  
   *To prevent hallucinations or misread names from corrupting production schedules. Staging enforces mandatory human HOS review.*  
   *Terms: Decoupled Pipeline, Zero Credentials, Human-in-the-Loop.*

10. **How is multi-tenant branch isolation enforced?**  
    *The user's department is locked in their signed session cookie; all SQL queries are parameterized by that department code.*  
    *Terms: Session Department Scope, Horizontal Authorization, HTTP 403.*

11. **How are sessions authenticated without JWT?**  
    *Using stateless HMAC-SHA256 signed cookies (`tec_session`) verified via constant-time buffer comparison (`timingSafeEqual`).*  
    *Terms: Stateless Signed Cookie, HMAC-SHA256, Constant-Time Comparison.*

12. **What happens if a substitute becomes busy before accepting?**  
    *Atomic revalidation at acceptance detects the conflict and aborts with HTTP 409 Conflict.*  
    *Terms: Race Condition Defense, Atomic Revalidation, HTTP 409.*

13. **How are multi-period laboratory practicals handled?**  
    *Expanded into atomic period slots in the database while visually rendered as merged multi-column spans in the UI.*  
    *Terms: Atomic Expansion, Colspan Rendering, Span Range.*

14. **What are your verified testing metrics?**  
    *30/30 database checks passed, 10 core entities persisted across restart, all 29 automated test suites passed, and 48/48 live verification checks passed.*  
    *Terms: 30/30 DB, 10 Persisted Entities, 29 Suites, 48/48 Live.*

15. **What are the main project limitations?**  
    *Requires internet connection for cloud DB/AI, handles 1-to-1 period substitutions rather than split periods, and uses session cookies rather than enterprise SSO.*  
    *Terms: Cloud Dependency, 1-to-1 Coverage, Session Authentication.*
