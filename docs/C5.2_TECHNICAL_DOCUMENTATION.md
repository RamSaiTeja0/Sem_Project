### AI Timetable Extraction Subsystem

The AI ingestion pipeline is strictly decoupled from the live operational tables:

```
[ HOS Browser ]
       │  1. Uploads Timetable Image / PDF
       ▼
[ TecSubstitution Backend (/api/uploads) ]
       │  2. Saves raw file to disk; creates 'UPLOADED' record in `timetable_uploads`
       │  3. Dispatches Webhook to n8n
       ▼
[ n8n Automation Engine / Runner ]
       │  4. Authenticates via X-Internal-Secret
       │  5. Fetches file binary and metadata from /api/internal/uploads/:id
       │  6. Forwards document binary + strict extraction prompt to Google Gemini
       ▼
[ Google Gemini Vision (gemini-2.5-flash) ]
       │  7. Analyzes visual grid and outputs structured JSON (Phase B2.1 Contract)
       ▼
[ n8n Automation Engine ]
       │  8. Delivers extracted JSON to /api/internal/uploads/:id/processed
       ▼
[ TecSubstitution Backend (/api/internal/uploads) ]
       │  9. Validates JSON schema, period bounds, days, and slot overlaps
       │ 10. Writes to `timetable_staging` table with status 'VALID' or 'INVALID'
       │ 11. Transitions upload status to 'PROCESSED'
       ▼
[ HOS Interactive Staging UI (/api/staging) ]
       │ 12. HOS inspects extracted matrix, resolves uncatalogued entities
       │ 13. HOS clicks APPROVE (or REJECT)
       ▼
[ Transactional Import Engine ]
       │ 14. Atomic execution: expands spans, checks cross-class conflicts,
       │     and imports records into the live `timetable` table.
```

> [!IMPORTANT]
> **Zero Direct Database Writes by AI**: Google Gemini and n8n never hold database credentials and cannot modify the live `timetable` table. Extracted data is held in an isolated staging table (`timetable_staging`) until an authorized human HOS inspects, maps, and approves the record.

## 3. USER ROLES

The application enforces a dual-role access control model:

### 1. Head of Section (HOS)
- **Administrative Scope**: Sole administrator of their designated academic branch (e.g., Computer Engineering).
- **Core Responsibilities**:
  - **Branch Profile**: Configures department name, code, academic year, and active semesters.
  - **Faculty Management**: Creates and updates faculty accounts, sets designations, and assigns login credentials.
  - **Catalog & Classes**: Defines class sections (e.g., CME-A, CME-B), rooms, and subject curricula.
  - **Master Timetable**: Adds, edits, and deletes class timetable entries across the 7 periods and 6 weekdays.
  - **Attendance**: Records daily faculty attendance (Present/Absent) with optional leave remarks.
  - **Exam Invigilation**: Schedules exam duties directly or approves/rejects faculty invigilation requests.
  - **Timetable Staging**: Uploads schedule images/PDFs, inspects AI extraction output, resolves uncatalogued faculty/subjects, and grants final approval for live insertion.
  - **Audit Visibility**: Views a read-only historical ledger of all faculty-to-faculty substitutions.
- **Explicit Boundaries**:
  - Cannot access, view, or modify other departments' faculty, classes, or timetables.
  - Cannot create, accept, or reassign faculty-to-faculty substitution requests.

### 2. Faculty Member
- **Instructional Scope**: Individual teaching staff member assigned to a specific branch.
- **Core Responsibilities**:
  - **Personal Timetable**: Views their personal weekly schedule with class sections, rooms, and subjects.
  - **Vacant Periods**: Inspects periods where they have no scheduled classes or invigilation duties.
  - **Availability Search**: Queries free faculty colleagues for any day and period, prioritized by branch.
  - **Substitution Requests**: Initiates substitution requests to eligible free colleagues for scheduled classes.
  - **Request Decision**: Accepts or declines incoming substitution requests dispatched by peers.
  - **Attendance Ledger**: Views a personal, read-only history of their recorded attendance.
  - **Invigilation Requests**: Submits requests for exam invigilation duties to the HOS.
- **Explicit Boundaries**:
  - Cannot modify the master class timetable or alter class schedule entries.
  - Cannot create other user accounts or alter department configuration.
  - Cannot mark or modify attendance records.
  - Cannot review or approve staged AI timetable imports.

## 4. AUTHENTICATION AND AUTHORIZATION

### Session-Based Authentication
TecSubstitution implements a stateless, cryptographically signed cookie architecture (`tec_session`), eliminating server-side session stores while guaranteeing tamper-proof security:

1. **Token Generation**: Upon successful login, the server packages user metadata (`id`, `username`, `name`, `role`, `department`, `facultyName`, `exp`) into a JSON string.
2. **Encoding & Signing**: The JSON is Base64URL-encoded and signed using HMAC-SHA256 with the server's private `SESSION_SECRET`:
   $$\text{Cookie} = \text{Payload} \,\|\, '.' \,\|\, \text{HMAC-SHA256}(\text{Payload}, \text{Secret})$$
3. **Verification**: On every incoming request, middleware parses the `tec_session` cookie, verifies the cryptographic signature using constant-time buffer comparison (`crypto.timingSafeEqual`), and checks the expiration timestamp. If invalid or expired, the session is invalidated immediately.

### Password Security & Policy
- Passwords are encrypted using secure cryptographic hashing before storage in the `users` table.
- Account creation enforces a strict complexity regex policy:
  - Minimum length: 6 characters.
  - Required characters: At least one uppercase letter (`A-Z`), one lowercase letter (`a-z`), one digit (`0-9`), and an underscore (`_`).
  - Prohibited: Spaces, special symbols outside underscore, and common weak passwords.

### Authorization & Multi-Tenant Branch Isolation
- **Role-Based Guards**:
  - `requireAuth`: Rejects unauthenticated requests with HTTP 401.
  - `requireHOS`: Restricts administrative routes to users with `role: 'hos'` (HTTP 403 for faculty).
  - `requireFaculty`: Restricts substitution initiation/decision routes to `role: 'faculty'` (HTTP 403 for HOS).
- **Branch Scoping**:
  - The authenticated user's branch (`department`) is embedded directly in the verified session payload.
  - All database queries for timetable entries, faculty rosters, attendance, and staging are automatically parameterized with `WHERE department_code = req.session.department`.
  - Cross-branch write attempts are intercepted and rejected with `HTTP 403 FORBIDDEN: Cross-branch access forbidden`.
- **Faculty Account Inheritance**:
  - Faculty members created by an HOS automatically inherit the HOS's branch code. Faculty cannot edit or reassign their departmental affiliation.
- **Account Deactivation**:
  - The `users` table includes an `active` boolean column. Deactivated accounts are rejected at login time, preventing access while preserving historical attribution.

## 5. TIMETABLE MANAGEMENT

The timetable management module governs the creation, scheduling, and validation of institutional class and faculty timetables.

### Data Dimensions
- **Academic Scope**: Branch Code (e.g., CME), Academic Year (e.g., 2025-2026), Semester (1 to 6), Section (A, B, etc.).
- **Temporal Grid**:
  - Days: Monday through Saturday.
  - Periods: Periods 1 through 7 (standard daily operational periods).
- **Session Types**:
  - `theory`: Standard 1-period instructional lectures.
  - `lab`: Multi-period practical laboratory sessions spanning 2 or 3 consecutive periods (e.g., Periods 1 to 3 or Periods 5 to 7).
  - `activity`: Non-instructional scheduled periods (e.g., Library, TPC/Placement, Sports, Counselling) which occupy class time but do not require faculty allocation.

### Conflict Prevention Rules
Every timetable insertion or edit is evaluated against three core invariants:
1. **Class Slot Integrity**: A specific class section cannot have more than one scheduled activity in the same day and period.
2. **Faculty Double-Booking Prevention**: A faculty instructor cannot be assigned to teach two different classes during the same day and period.
3. **Room Double-Booking Prevention**: A physical classroom or laboratory venue cannot host two different classes during the same day and period.

### Entity Resolution and Human-in-the-Loop Governance
1. **Zero Silent Creation**: The backend prohibits creating new faculty, subjects, or rooms automatically based on LLM output.
2. **Resolution Check**: Extracted text (e.g., "M.DALAYYA") is cross-referenced against the active branch catalog. If no exact match is found, it is flagged as `UNRESOLVED`.
3. **HOS Entity Mapping**: The HOS uses the mapping interface to link the extracted string to an existing catalog entity.
4. **Approval Gate**: The `POST /api/staging/:uploadId/approve` endpoint strictly rejects any attempt to import a timetable if unresolved entities remain.

## 7. FACULTY ATTENDANCE

Faculty attendance directly drives the dynamic availability calculation:

1. **Default Status**: In the absence of an explicit attendance record, a faculty member is presumed **PRESENT** for scheduled duties.
2. **HOS Absence Logging**: The HOS marks a faculty member **ABSENT** for a specific calendar date (`YYYY-MM-DD`) via `POST /api/attendance`. An optional remark (e.g., "Sick Leave", "On Duty") may be attached.
3. **Date-Specific Scope**: Absence is recorded per calendar date and does not permanently modify the faculty member's profile or recurring weekly timetable.
4. **Availability Filtering**: When availability is calculated for a given calendar date, all faculty marked `ABSENT` on that date are excluded from the pool of eligible substitutes.
5. **Self-Service View**: Faculty members can query `GET /api/attendance/my` to view a personal, read-only history of their recorded attendance.

## 8. FACULTY AVAILABILITY

The **Availability Engine** is a high-performance, read-only evaluation service (`src/routes/availability.js`) that determines which faculty members are eligible to take a substitution:

$$\text{Faculty Status} = \begin{cases} 
\text{BUSY}, & \text{if Faculty is INACTIVE} \\
\text{BUSY}, & \text{if Faculty is marked ABSENT on Date} \\
\text{BUSY}, & \text{if Faculty has a Scheduled Class in Master Timetable} \\
\text{BUSY}, & \text{if Faculty has an Active Exam Invigilation in Period} \\
\text{BUSY}, & \text{if Faculty has an Accepted Substitution in Period} \\
\text{FREE}, & \text{otherwise}
\end{cases}$$

### Candidate Prioritization
To minimize inter-departmental disruption, available candidates are partitioned into two priority tiers:
1. **Priority Branch (Local Department)**: Free faculty belonging to the same department as the absent instructor.
2. **Other Branches (Allied Departments)**: Free faculty belonging to other registered branches in the institution, displayed to ensure coverage when local staff are fully engaged.

## 9. EXAM INVIGILATION

Exam invigilation accounts for examination hall supervision duties:

- **HOS Direct Assignment**: An HOS can directly assign a faculty member to invigilate an examination during specific periods on a calendar date (`POST /api/invigilation`).
- **Faculty Invigilation Requests**: A faculty member can request invigilation duty for specific periods on a date (`POST /api/invigilation/requests`). The HOS can review, approve, or reject this request.
- **Operational Impact**: An assigned invigilation slot marks the faculty member as **BUSY** for that specific period in the availability engine. 
- **Distinction from Absence**: Invigilation duty does *not* mark a faculty member absent; the faculty member is on active institutional duty on campus.

## 10. FACULTY-TO-FACULTY SUBSTITUTION

TecSubstitution implements a peer-to-peer substitution workflow (**Option A**) that empowers instructors while keeping departmental leadership informed:

```
[ Absent Faculty A ]
         │
         │  1. Inspects personal schedule; identifies vacant period
         │  2. Queries free candidates via Availability Engine
         │  3. Selects free Faculty B; submits request
         ▼
[ POST /api/substitutions/requests ]
         │
         │  4. Creates record in `faculty_substitutions` (Status: 'PENDING')
         ▼
[ Faculty B Incoming Portal ]
         │
         │  5. Reviews incoming request details (Class, Subject, Room, Date, Period)
         │
         ├──► [ REJECT ] ──► Status updated to 'REJECTED'
         │
         └──► [ ACCEPT ]
                  │
                  ▼
         [ Real-Time Revalidation ]
         - Verifies Faculty B is STILL free on that date/period
         - Verifies no simultaneous conflict has emerged
                  │
                  ▼
         [ Status: 'ACCEPTED' ]
         - Stored in `faculty_substitutions`
         - Faculty B is now marked BUSY for that slot
         - Master Timetable remains 100% UNTOUCHED
```

- **HOS Oversight**: The HOS has read-only visibility into branch substitutions (`GET /api/substitutions`) for administrative auditing, but cannot accept or reject peer requests.

## 12. API / BACKEND FLOW

The system exposes RESTful HTTP endpoints organized by functional domain:

### Authentication (`/api/auth`)
- `GET /api/auth/session` — Returns active session status and public user profile.
- `GET /api/auth/status` — Returns institutional setup status, active branch, and HOS presence.
- `GET /api/auth/branches` — Returns list of registered academic departments.
- `POST /api/auth/register` — Registers a new HOS or Faculty user account.
- `POST /api/auth/login` — Authenticates credentials and issues signed `tec_session` cookie.
- `POST /api/auth/logout` — Clears the session cookie.

### Timetable Entries (`/api/timetable/entries`)
- `GET /api/timetable/entries` — Lists timetable entries with optional filtering by class, day, and period.
- `GET /api/timetable/entries/reference` — Provides dropdown reference values (classes, subjects, faculty, rooms).
- `POST /api/timetable/entries` — Adds a new class timetable entry (HOS only, conflict validated).
- `PUT /api/timetable/entries/:id` — Updates an existing timetable entry (HOS only).
- `DELETE /api/timetable/entries/:id` — Removes an entry and vacates the class slot (HOS only).

### Availability Engine (`/api/availability`)
- `POST /api/availability` — Evaluates and returns free faculty candidates for a `{ day, period, date, absentFaculty }`.
- `GET /api/availability` — Read-only query version for timetable inspection.
- `GET /api/availability/summary` — Returns aggregate availability metrics for the dashboard.

### Faculty Attendance (`/api/attendance`)
- `GET /api/attendance?date=YYYY-MM-DD` — Lists branch faculty attendance for a date (HOS only).
- `POST /api/attendance` — Marks a faculty member ABSENT or PRESENT on a date (HOS only).
- `DELETE /api/attendance/:id` — Removes an attendance record, restoring default PRESENT (HOS only).
- `GET /api/attendance/my` — Read-only self-view of attendance history for authenticated faculty.

### Exam Invigilation (`/api/invigilation`)
- `POST /api/invigilation` — Assigns invigilation duty directly (HOS only).
- `GET /api/invigilation` — Lists active invigilation assignments for branch (HOS only).
- `DELETE /api/invigilation/:id` — Cancels an invigilation assignment (HOS only).
- `POST /api/invigilation/requests` — Submits invigilation duty request (Faculty only).
- `GET /api/invigilation/requests` — Lists pending invigilation requests (HOS only).
- `POST /api/invigilation/requests/:id/approve` — Approves invigilation request (HOS only).
- `POST /api/invigilation/requests/:id/reject` — Rejects invigilation request (HOS only).
- `GET /api/invigilation/my` — Returns personal invigilation assignments (Faculty only).

### Substitutions (`/api/substitutions`)
- `POST /api/substitutions/requests` — Initiates peer substitution request (Faculty only).
- `GET /api/substitutions/incoming` — Fetches pending incoming requests for review (Faculty only).
- `POST /api/substitutions/:id/accept` — Accepts substitution with live revalidation (Faculty only).
- `POST /api/substitutions/:id/reject` — Rejects substitution request (Faculty only).
- `DELETE /api/substitutions/:id` — Cancels a pending request (Initiator Faculty only).
- `GET /api/substitutions` — Returns branch substitution history ledger (HOS only, read-only).

### Document Uploads & Staging (`/api/uploads`, `/api/staging`, `/api/internal/uploads`)
- `POST /api/uploads` — Uploads timetable image or PDF (HOS only).
- `GET /api/staging/pending` — Lists staged extractions pending review (HOS only).
- `GET /api/staging/:uploadId` — Fetches extracted contract JSON and entity resolution status (HOS only).
- `POST /api/staging/:uploadId/map-entity` — Maps extracted text to a catalog entity (HOS only).
- `POST /api/staging/:uploadId/approve` — Executes transactional live import of valid staged timetable (HOS only).
- `POST /api/staging/:uploadId/reject` — Rejects staged timetable with a recorded reason (HOS only).
- `POST /api/internal/uploads/:uploadId/processed` — Receives JSON from n8n pipeline (`X-Internal-Secret` protected).

## 13. SECURITY AND DATA ISOLATION

TecSubstitution is engineered with multiple defensive layers:

1. **Stateless Signed Cookie Integrity**: Sessions cannot be forged without knowing `SESSION_SECRET`. Payload modification invalidates the HMAC signature immediately.
2. **Strict Multi-Tenant Branch Isolation**: All administrative queries are scoped by department code. HOS A cannot read or write records belonging to HOS B.
3. **Database-Level Defense**:
   - Parameterized SQL statements throughout all queries prevent SQL injection.
   - Foreign key constraints prevent orphaned records.
   - Partial unique indexes prevent double-booking at the database engine level.
4. **Filesystem Isolation**: Uploaded documents are saved outside public static directories. Direct web requests to `/uploads` return HTTP 404.
5. **Automation Secret Shield**: Service-to-service endpoints (`/api/internal/*`) reject any caller lacking the matching `X-Internal-Secret` header.
6. **Zero Plaintext Secrets in Client Code**: Google Gemini API keys and database connection strings exist solely in environment variables and are never transmitted to browsers.

### A. Normal Timetable Entry Management
```
HOS selects Class & Period -> Fills form (Subject, Faculty, Room) ->
POST /api/timetable/entries -> Server validates slot & double-booking ->
```

### B. AI Timetable Upload & Ingestion
```
HOS uploads PDF/Image -> Server creates `timetable_uploads` record ->
Webhook fires -> n8n invokes Gemini Vision -> Gemini returns B2.1 JSON ->
n8n sends to `/api/internal/uploads/.../processed` -> Server validates JSON ->
Stored in `timetable_staging` -> HOS reviews & maps entities ->
HOS clicks APPROVE -> Transactional import commits entries to `timetable`.
```

### C. Faculty Absence to Availability Filtering
```
HOS marks Faculty A ABSENT on Date -> Recorded in `faculty_attendance` ->
Faculty B queries Availability for that Date & Period ->
Availability Engine excludes Faculty A and busy teachers ->
Returns grouped list of available faculty (Same Branch first).
```

### D. Faculty-to-Faculty Substitution
```
Absent Faculty A selects free Faculty B -> Submits substitution request ->
Record created in `faculty_substitutions` (PENDING) ->
Faculty B views incoming request -> Clicks ACCEPT ->
Server rechecks Faculty B's real-time availability ->
Marks substitution ACCEPTED -> Faculty B marked busy; Master Timetable untouched.
```

### E. Exam Invigilation Assignment
```
HOS assigns Faculty A to Room C-401 for Period 2 on Date ->
Record created in `exam_invigilation` ->
Availability Engine automatically marks Faculty A BUSY during Period 2 ->
Faculty A views assignment in personal dashboard.
```

## 15. ERROR AND CONFLICT HANDLING

| Conflict Scenario | Detection Layer | System Response & Resolution |
| :--- | :--- | :--- |
| **Class Slot Double-Booking** | Application & SQL Constraint (`timetable_class_slot_unique`) | Request rejected with HTTP 409 Conflict: *"Class already has an entry for this slot."* |
| **Faculty Double-Booking** | Application & Partial Unique Index (`timetable_faculty_slot_unique`) | Request rejected with HTTP 409 Conflict: *"Faculty is already teaching another class during this period."* |
| **Room Double-Booking** | Application & Partial Unique Index (`timetable_room_slot_unique`) | Request rejected with HTTP 409 Conflict: *"Room is already occupied by another class."* |
| **Cross-Branch Mutation** | Express Middleware Guard | Request blocked with HTTP 403 Forbidden: *"Cross-branch queries are not allowed."* |
| **Concurrent Substitution Acceptance** | Transactional Revalidation Guard | If a candidate was booked elsewhere between request and acceptance, acceptance fails with HTTP 409: *"Substitute is no longer free."* |
| **Duplicate User Registration** | Unique Index on `users(username)` | Rejection with HTTP 400 Bad Request: *"Username already exists."* |
| **Weak Password** | Authentication Validator Regex | Rejection with HTTP 400: *"Password must have min 6 chars, uppercase, lowercase, number, and underscore."* |
| **Unresolved AI Entities** | Staging Gatekeeper (`resolveContract`) | Staging approval blocked with HTTP 422 Unprocessable Entity: *"Cannot approve: Unresolved extracted references."* |
| **Corrupted / Invalid AI Schema** | Contract Validator (`validateContract`) | Staging marked `validation_status: 'INVALID'`, logging detailed schema syntax errors and preventing approval. |
